# Face Recognition Accuracy & Threshold Calibration

## Run the benchmark yourself

```bash
cd raspberry_pi
python3 benchmark.py
```

No extra dependencies beyond `requirements.txt` (`numpy`, `opencv-python-headless`).
Measures pipeline latency, embedding latency, quality-gate correctness, and
recognition metrics against synthetic frames generated in-process — no
camera or network required. Section headers in its output distinguish
dev-mode pipeline validation (classical embedder, synthetic faces) from
what a real deployment needs.

Three related tools, for once you have the real model installed:
- `python3 embedding_model.py --info` / `--self-test` — confirm the model
  file loads and its I/O shapes match spec (see `docs/EMBEDDING_SPEC.md`).
- `python3 webcam_test.py` — live test against your own face
  (`docs/LOCAL_WEBCAM_TESTING.md`).
- `python3 calibrate_threshold.py --data-dir <real photos>` — real FAR/FRR/
  EER/ROC from real genuine/impostor pairs (this section, below).

## Latency — actual results from this pass (sandbox CPU, not a Raspberry Pi)

| Metric | Value |
|---|---|
| Single-face: detection-only (approx) | 12.5 ms |
| Single-face: embedding-only (batch of 1) | 0.4 ms |
| Single-face: combined | 12.9 ms (~78 FPS implied ceiling) |
| Four-face: combined | 37.3 ms (~27 FPS implied ceiling) |
| Faces detected per 4-face synthetic frame | 4/4 consistently |
| Quality gate: good frame reaches consensus | Yes |
| Quality gate: bad (blurred+dark) frame reaches consensus | No |

Detection (Haar cascade) dominates latency by roughly 30x over embedding —
the classical embedder is nearly free by comparison. This means swapping in
the (heavier) ONNX deep model later will cost real FPS, and batching (all 4
faces embedded in one `embed_batch()` call, not 4 separate calls) matters
more once that swap happens than it does today.

**Read these as relative/algorithmic numbers, not a hardware SLA** — this
sandbox's CPU is not a Pi 4/5. Re-run on real hardware before trusting the
FPS figures; see `benchmark.py`'s own printed guidance for what to do if a
Pi can't sustain 4-face throughput at the configured `camera_fps`.

## Recognition accuracy — actual measured results (NOT estimated, and NOT good)

Using the real `HOGLBPEmbedder` (`embedding_model.py`) against 6
visually-distinct synthetic faces (parametric ellipse faces with varied eye
spacing, jaw width, and skin tone — see `benchmark.py`'s `IDENTITY_PARAMS`
and `make_face()` — this is **not** a real photo dataset; see the caveat
below), `benchmark.py` measures the real genuine/impostor similarity
distributions and sweeps for the empirical equal-error-rate point rather
than assuming a threshold:

| Metric | Measured value |
|---|---|
| Genuine (same-identity) similarity | min 0.966, mean 0.974, max 0.982 |
| Impostor (different-identity) similarity | min 0.942, mean 0.963, max 0.982 |
| Measured equal-error-rate threshold | 0.9704 |
| False accept rate at that threshold | ~20% |
| False reject rate at that threshold | ~20% |

**Read this plainly, not optimistically:** the genuine and impostor
distributions *overlap* (genuine's minimum, 0.966, is below impostor's
maximum, 0.982) — no threshold perfectly separates them. ~1 in 5
comparisons is wrong at the best achievable operating point. For
comparison, production deep-learning face recognition (ArcFace/FaceNet-
class models) typically achieves well under 1% equal-error-rate on standard
benchmarks like LFW. This is a genuine, measured limitation of classical
gradient/texture features on faces without strong distinguishing structure,
not a bug in the matching logic — `identity_matcher.py`'s RECOGNIZED /
UNKNOWN / AMBIGUOUS logic was independently verified correct (see its own
unit tests); it's the discriminative power of the *input* it's fed that's
limited.

**Why this specific number and not a rounder one:** per the instruction not
to blindly choose a threshold, `0.9704` is the actual empirical crossover
point of the measured distributions above, not a guess. `FACE_MATCH_THRESHOLD`
in `route.ts` / `device_manager.py` has been set to `0.97`
(`HIGH_CONFIDENCE_THRESHOLD` to `0.975`, `AMBIGUOUS_MARGIN` to `0.01`) to
match. If you change the embedder (see "Switching to the ONNX backend"
below), **these thresholds become meaningless for the new embedder and must
be re-measured** — they are calibrated to this specific feature space, not
a universal constant. Re-run `benchmark.py::bench_recognition()` after any
embedder change.

### Why this can't be trusted as a real accuracy number

The 6 "identities" above are simple parametric shapes generated by
`make_face()`, not photos of real people. Real faces have far more subtle,
individual-specific structure (skin texture detail, asymmetries, hair,
expressions) that this synthetic generator doesn't model at all — both in
ways that could make real discrimination easier (more distinguishing
detail) or harder (more within-person variation across lighting/pose/
expression than the simple translation+noise jitter used here). Treat the
FAR/FRR numbers above as "this pipeline can measure and report real
accuracy metrics, and here's what it found on the one dataset available in
a network-isolated sandbox" — not as "this is what accuracy will be on your
bus." Measuring real accuracy requires real enrollment photos; see the
labeled-pairs methodology further down.

## Two real bugs an earlier benchmarking pass found and fixed (liveness)

Kept here for continuity — these predate the embedding-model swap and are
unrelated to it:

1. **Liveness was measured over the whole frame, not per face**, diluting a
   small face's real motion into the static background average. Fixed:
   liveness is now computed per-face, from each face's own crop against its
   own crop in the previous frame.
2. **The liveness score was floored at 0.7 regardless of actual motion.**
   Fixed: the reported score now reflects the actual measured value.

Full writeup: `docs/FACE_RECOGNITION.md`, "Liveness / anti-spoofing" section.

## Configurable thresholds

All served from `GET /api/v1/iot/device/config` (see `API_IOT.md`), consumed
via `device_manager.threshold(name)`. **These are calibrated to the
classical `HOGLBPEmbedder` currently active** — re-measure if the embedder
changes:

| Threshold | Default | Meaning |
|---|---|---|
| `BLUR_VARIANCE_MIN` | 60.0 | Laplacian variance floor; below this, `quality.isAcceptable = false` |
| `TEMPORAL_WINDOW_FRAMES` | 8 | Sliding window size a track's frame history is capped at |
| `TEMPORAL_MIN_FRAMES` | 5 | Consecutive acceptable+live frames required before a track submits |
| `FACE_MATCH_THRESHOLD` | 0.97 | **Measured** equal-error-rate point for `HOGLBPEmbedder` (see above) |
| `HIGH_CONFIDENCE_THRESHOLD` | 0.975 | Above this, treat a `RECOGNIZED` match as high-confidence |
| `LOW_CONFIDENCE_THRESHOLD` | 0.94 | Below this, treat as low-confidence / lean toward unknown |
| `LIVENESS_THRESHOLD` | 0.05 | Cutoff on the per-face local motion score (see `FACE_RECOGNITION.md`) |
| `AMBIGUOUS_MARGIN` | 0.01 | If the top two candidates' similarity scores are within this margin, return `AMBIGUOUS` rather than guess |

**Important caveat on `lib/server-db.ts`:** that file has its own,
completely independent `SIMILARITY_THRESHOLD` (`process.env.FACE_MATCH_THRESHOLD`,
default `0.72`), used for matching against the browser's differently-generated
embeddings. Changing the table above does **not** change that. See
`FACE_RECOGNITION.md`'s "embedding-space mismatch" section — this is the
most important thing to understand before assuming end-to-end recognition
works.

## How to calibrate `BLUR_VARIANCE_MIN` and `TEMPORAL_MIN_FRAMES` against real footage

(Unchanged from before — these don't depend on which embedder is active.)

1. Collect a short clip (or a batch of stills) from the actual mounted
   camera at the actual door, across a few lighting conditions.
2. For each frame, run it through `FrameFaceDetector.process()` directly and
   record `quality.blur` for frames a human would call "good enough" vs.
   "too blurry." Pick `BLUR_VARIANCE_MIN` around the 10th percentile of the
   "good enough" set.
3. For `TEMPORAL_MIN_FRAMES`, weigh dwell time directly:
   `TEMPORAL_MIN_FRAMES / camera_fps` is the minimum time a passenger must
   stand still-ish in frame before being submitted. Tune against observed
   boarding pace.
4. Re-run `benchmark.py::bench_quality_gate()` after changing
   `BLUR_VARIANCE_MIN` via `config.json`'s `threshold_overrides`.

## How to calibrate `FACE_MATCH_THRESHOLD` against real enrolled students

**Use `raspberry_pi/calibrate_threshold.py` — don't hand-roll this.** It:

1. Loads real photos from `calibration_data/<person_id>/*.jpg` (multiple
   photos per person — the existing multi-angle enrollment capture
   front/left/right/up/down is a natural source).
2. Embeds every photo with the real `ONNXFaceEmbedder` (batched) —
   **refuses to run** against the dev-mode `HOGLBPEmbedder` unless you pass
   `--allow-dev-embedder` (and even then, loudly labels the result as
   meaningless for the real model — see "Two intermediate fixes" below).
3. Computes genuine (within-person) and impostor (across-person) cosine
   similarity distributions directly from real data.
4. Sweeps thresholds, reports **FAR, FRR, TAR, TRR, and the empirical
   equal-error-rate operating point**, plus ROC AUC if `scikit-learn` is
   installed.

```bash
cd raspberry_pi
python3 calibrate_threshold.py --data-dir calibration_data/
```

**Verified (math only, not the real model):** this script's FAR/FRR/EER/ROC
math was run end-to-end against a synthetic dataset (6 synthetic
identities, 4 images each, `--allow-dev-embedder`) in the sandbox that
built it, and produced internally-consistent results (EER threshold 0.9451,
FAR 22.5%, FRR 22.2%, ROC AUC 0.84 — in the same ballpark as the
independently-computed numbers earlier in this doc, which is a useful cross-
check that the sweep/EER logic itself is correct). **This is not a real
accuracy number** — it's confirmation the calibration math works, run
against the same limited synthetic data as everything else in this doc
until real photos and real model weights are available.

Once you have real results, pick the operating point your deployment cares
about — for boarding access control, biasing toward lower FAR (fewer
wrong-person boards) at some cost to FRR (occasional legitimate re-scans)
is usually right, since a false reject just means "try again" while a false
accept is a security/fee-evasion issue.

## Installing the real ONNX model (the chosen production path)

1. On a machine with network access, obtain `w600k_mbf.onnx` per
   `docs/EMBEDDING_SPEC.md`'s exact instructions, and place it at
   `raspberry_pi/models/face_embedding.onnx` (and `models/face_embedding.onnx`
   for the Node backend — same file, both places).
2. `pip install onnxruntime` (already present in the sandbox that wrote
   this doc, version 1.24.4 — but still untested against a real model file
   there for lack of network to fetch one).
3. Run `python3 embedding_model.py --self-test` to confirm the file loads
   and its shapes match spec before trusting anything downstream.
4. `embedding_model.build_default_embedder()` picks the real model up
   automatically from the default path — no config changes needed unless
   you placed it somewhere else (`config.json`'s `embedding_model_path`).
5. **Run `calibrate_threshold.py` against real photos and re-derive every
   threshold in the table above.** A deep model's similarity distribution
   has a completely different shape than the classical embedder's (expect
   much better separation — genuine scores clustering high, impostor scores
   clustering low, likely with the useful threshold somewhere in the 0.3-0.6
   cosine range rather than 0.97, though don't assume that number either —
   measure
   it). Carrying over the classical embedder's `0.97` threshold to a deep
   model would reject almost every genuine match.
